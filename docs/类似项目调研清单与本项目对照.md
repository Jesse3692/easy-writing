# 类似项目调研清单与本项目对照

> 整理日期：2026-09-29
> 输入：六位审计员对 easy-writing 仓库的 23 项逐项盘点（结论原样保留于第一~七节，含 path:line 证据）
> 配套输入：`docs/竞品拆书技术分析-InkOS.md`（横向对比表 InkOS 列的唯一来源）
> 用途：研究每一个"类似项目"（拆书 / 角色抽取 / 多角色模拟 / 小说辅助创作类软件）时的对照基准

## 0. 文档目的与使用方法

### 0.1 目的

团队即将系统研究若干类似项目，方法论固定为三层：**它解决了什么问题 → 它为什么这样设计 → 哪些实现能安全迁移到本项目**。
本文档是第三层的前置家底：把 23 项调研清单逐项落到 easy-writing 的现状上，使每研究一个新项目都能回答"对方做到几分、我们做到几分、差在哪、落到哪个目录"。

### 0.2 easy-writing 一句话定位

**纯本地的网文写作桌面软件**：作品、设定与写作记录存在用户本机（SQLite + IndexedDB + localStorage 三层存储），无需注册登录，基础写作可离线；AI 能力经 BYOK 直连 OpenAI 兼容模型，覆盖写作辅助、竞品拆书与榜单风向三条链路；单用户桌面形态（Tauri 2，`src-tauri/Cargo.toml:20`），无自建服务端、无 Docker、无 CI——后三项的逐项核查见第六节清单 20/21（`README.md:3`、`README.md:7`）。

### 0.3 借鉴优先级原则

按对本项目的边际收益排序，**前面的没补完，不碰后面的**：

1. **数据协议**（数据结构、主键、schema_version、evidence 指针、产物指纹）——决定历史数据能否安全升级与复现；
2. **失败处理**（断点续跑、重试不重付、孤儿修复、原子写、失败即回退）——决定长任务可信度；
3. **评估方法**（评估维度、LLM-as-judge、基准集、方差对比）——决定质量能否被度量；
4. **人工复核流程**（候选账、needs_review 队列、合并/拆分/撤销）——决定 AI 产物能否被信任地采用；
5. **最后才是 UI 与 prompt 文案**——本项目提示词体系已完成到"14 个 md 场景文件 + 槽位 + 槽级温度 + 指纹升级"（`docs/提示词系统技术实现.md:28-31`），对方 prompt 文案的参考价值最低，只在其输出契约（证据/推断分离、结构约束）层面借鉴。

### 0.4 使用方法（逐项对照打分）

1. 研究新项目时，先按第九节《统一调研报告模板》18 字段填写；
2. 回到第一~七节 23 项，用同一套口径给对方打分，与本项目成熟度并排；
3. 差距 = 对方成熟度 − 本项目成熟度；**差距 ≥ 2 档且属于 0.3 节前四类的，进优先借鉴池**；
4. 每条借鉴填第八节对比表的"落点"列（用本项目实际目录名），并配第十节的验收方式；
5. UI 与 prompt 文案类差异只记录、不进池。

**成熟度口径**（沿用审计员评级，共四档，无一项达到"完善"）：

| 档位 | 含义 | 本次项数 |
|---|---|---|
| 缺失 | 全库找不到对应实现 | 4（清单 6、8、10、13） |
| 基础 | 有数据结构或雏形，缺关键机制 | 10（清单 3、4、7、9、11、12、14、15、19、21） |
| 可用 | 主链路可用，边缘场景有欠账 | 6（清单 5、16、17、18、20、22） |
| 较完善 | 机制完整，仅边缘场景有欠账 | 3（清单 1、2、23） |

## 一、优先获取的核心内容

### 1. 项目定位与目标用户

- **现状**：定位在 README 与代码中高度一致：纯本地、开源、BYOK 的网文写作桌面软件，无需注册登录，基础写作可离线（`README.md:3`、`package.json:5`）。核心用户是网文作者——起点/番茄/七猫/晋江平台作者与想把稿子攥在自己手里的写作者（`README.md:7`）。用户最常完成的三件事：① 写作台写正文并管章节（编辑器 / 160ms 级自动保存 / 历史版本，`README.md:34-36`；`docs/开发启动指南.md` 未提自动保存细节；写作从『我的作品』进入具体书籍，侧栏一级菜单首项是首页 `src/config/navigation.ts:12-19`）；② 配置 BYOK 模型后用 AI 辅助（划词润色 / 续写 / 对话 / 工作流建书，`README.md:51-59`、README.md:86）；③ 调研类任务：竞品拆书（TXT 逐章拆解）与榜单风向（本机爬虫 + 趋势，`README.md:57`、`README.md:61-63`）。主要痛点是数据自主、AI 费用自控、提示词可改（`README.md:25-28`）。核心能力是写作编辑器与本地数据主权；打字音效 / 光标特效 / 四套主题是体验增强层（`README.md:43-49`），榜单爬虫是桌面版限定的工具层（`README.md:115-116`），均不阻断主创作链路。忠实性上拆书忠于原文（导入 TXT 后逐章拆解、正文原样存储、分析单独成产物，`src/storage/local-breakdown.ts:23-30`），工作流建书则是从灵感出发的自由创作（`docs/工作流建书技术实现.md:8-12`）。

### 3. 数据结构与数据契约

- **现状**：拆书域数据结构见 `src/types/breakdown.ts`：每章 analysis 含 summary / outline（节点带段落区间 range）/ rhythm / setting / relations（`{from,to,relation,desc}` 纯名字字符串）/ golden（前三章深拆，anchors 带原文摘句）；全书报告 report 是无类型 `JsonRecord`，字段散落在提示词默认形状里（`editorNotes` / `outlineRecovery` / `characterArcs` / `foreshadowLedger` / `pacingCurve` / `reusableTechniques`）。角色没有实体结构，只有项目级 `characterNames` 字符串数组。evidence 有两种弱形态：段落序号映射 `paragraphInsightIds` 与 `golden.anchors` 摘句，均无字符偏移。写作参考面板（`BookReferenceDoc`）有完整类型化实体（角色/关系/时间线事件/故事线/正文锚点 `PlotBinding.anchorStart`-`anchorText`），但是手工录入、与拆书数据零打通。

## 二、抽取与内容理解

### 4. 文本切块策略

- **现状**：切块是「章节优先」：`parseLocalTxtBook` 用正则识别卷名/章名（第X卷/第X章/节/回，含中文数字序号解析与标题行排雷），无章节时整书当一章；随后按 `\n+` 切段落数组，整章一次性送模型，无 token 切分、无 overlap、无语义/分层切块。字符偏移不保留——提示词里段落以 `[n]` 编号传递，AI 返回 `startPara`/`endPara` 段落号，再映射回 insightIds 数组下标，最细只能定位到「第几段」。超长章节只做静默截断（前 400 段）；界面无任何提示——全仓 grep `src/views/BookBreakdown/` 无 400/截断/超长相关提示文案。中文章节号与编码兼容做得较好（BOM / UTF-16 无头兜底 / GB18030 / 零字节清洗）。对话与叙述不区分。跨块连接几乎不存在：每章独立拆解，唯一聚合是全书的汇总报告，而报告只喂每章 summary + rhythm 文本。
- **成熟度**：基础
- **缺口**：超长章被 `slice(0,400)` 静默截断且界面无任何提示，后半章直接不参与拆解；同时缺 overlap 与字符偏移，跨章事件/关系没有任何连接机制。
- **借鉴落点**：`src/utils/local-breakdown-engine.ts`（`CHAPTER_MAX_PROMPT_PARAGRAPHS` 处）+ `src/config/breakdown-prompts.ts`（分层切块 / 重叠 / 字符偏移编号）

### 5. Prompt 设计方法

## 十、先研究什么、先借鉴什么（优先级建议）

结合第一~七节缺口，按"差距 × 可迁移性"排序。每条给出验收方式——做到即算借鉴落地。

### 高优先级

1. **本地全文检索内核（FTS5 + 中文分词 + 可重建投影）**——家底是四项完全缺失能力之一（清单 8：全库无 BM25/向量/FTS，搜索均为 JS 子串，`src-tauri/Cargo.toml:25`），而 InkOS 已验证 281 行零外部依赖可落地（`docs/竞品拆书技术分析-InkOS.md:33-44`）。**先研究 A/B 两个类似项目的检索实现，再动手。**
   验收：Rust 侧 FTS5 外部内容表 + 中文分词落地并对设定库/历史章节/拆书产物建索引；`AiChatPanel` 召回结果带 `charStart-charEnd` 指针可跳回原文；删除 DB 后可整库重建且内容不变。
2. **实体对齐与拆书侧人工复核闭环**——人物计数当前不可信：「小林/林川」算两个角色、名字用户从不可见（`src/utils/local-breakdown-engine.ts:102-109`、`src/storage/local-breakdown.ts:121`），而清单 6/15 双双评为缺失/基础。这是类似项目的典型能力，必须成体系借鉴（别名合并、同名区分、LLM 仲裁、needs_review）。
   验收：拆书产物出现稳定实体 ID + 别名表 + needs_review 队列；工作台可合并/拆分/改关系端点且有撤销；项目卡片「主要角色 N 人」与去重后实体数一致。
3. **失败案例登记簿 + 测试可入库 + 最小 CI**——"179 全绿"从未进入 git（`.gitignore:14` 挡掉 `tests/`，commit `fb53aa8` 只改了源码），无 CI 意味着所有质量结论都不可复现（清单 13/21）。
   验收：`.gitignore` 放开 `/tests/`；`parseAiJson` 脏输出样例与拆书 relations 端点正反例入库并在 CI 跑；新建 `.github/workflows/` 跑 `pnpm check` + `cargo test` + `check:contrast`，提交即验。

### 中优先级

1. **数据协议三件套：schema_version + 模型/提示词指纹 + 字符偏移 evidence**——拆书 IndexedDB 版本硬编码 1 无 upgrade（`src/storage/local-breakdown.ts:44`）、产物不留生成模型（`src/storage/local-workflow.ts:295-305`）、汇总丢 evidence（`src/utils/local-breakdown-engine.ts:216-231`）。
   验收：拆书/工作流产物带 `schema_version` 与模型/提示词指纹；改默认提示词后旧产物被标记过期或可区分版本；汇总报告每条论断带证据指针；旧版本数据有迁移分支而非静默丢。
2. **世界状态投影（逐章 truth + baseline + 钩子账本）**——建书后改大纲不级联（`src/utils/local-workflow-control.ts:100-102`）、章间无状态更新（`src/utils/local-workflow-writer.ts:700-980`），对应 InkOS 的 settleChapterState 逐章重放（`docs/竞品拆书技术分析-InkOS.md:109-117`）。
   验收：逐章生文把正文明确事实增量写回 run 级 state 且下一章上下文消费它；建书后改大纲/设定能标记已落地卷章失效并触发重建；待回收钩子有账本。
3. **LLM 评审轨落地 + consistency 空壳换真检查**——critic 契约已预留但恒 unavailable、consistency 恒 true 是典型假绿（`src/utils/local-quality-check.ts:124`、`src/utils/local-workflow-engine.ts:345-347`）。
   验收：critic 轨按固定场景产出 scores（至少覆盖人设/事实/关系一致性三维）；consistency 显示真实检查结果；固定测试场景多次运行方差可对比。

### 低优先级

1. **大数据量浏览治理（虚拟列表 + 关系图节点量）**——章目录/拆书章节列表全量 v-for、关系图一次拉 500 无治理（清单 16）。
   验收：千章规模下章目录滚动无明显掉帧（或明确分页）；关系图有聚合/懒加载策略。
2. **运行级性能档案**——首跑 vs 二跑、阶段占比、重试率、峰值内存全部无记录（清单 19）。
   验收：一次完整拆书/建书运行可导出聚合性能档案（耗时/token/重试率），界面可见阶段占比。
3. **第三方署名 NOTICE + 更新端点可配置**——Font Awesome CC BY 4.0 署名未落实（`package.json:49`）；更新检查强绑 GitHub 与 yichuang.xyz（`src-tauri/tauri.conf.json:56-58`）。
   验收：仓库根有 THIRD_PARTY/NOTICE 覆盖全部需署名依赖；更新源可指向自托管端点。
